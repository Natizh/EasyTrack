# Recurring payment reconciliation

[EasyTrack](../../README.md) · [Documentation](README.md) · English / [Italiano](../it/RECURRING_RECONCILIATION.md)

This document describes the original schema-6 reconciliation design and its format-7 tests. The current app uses SQLite schema 13 and JSON backup format 15; see [backup and restore](BACKUP_RESTORE.md). Current reimbursement and cash-flow totals follow the [financial accounting policy](FINANCIAL_ACCOUNTING.md).

EasyTrack keeps scheduled payments and real financial movements separate until a payment is recorded or linked. A recurring due date creates an `expected` occurrence and advances its rule cursor in one SQLite write transaction. It creates **no transaction** and changes no financial total. The due-day scan also proposes eligible existing Activity movements from the same managed account and kind, within the configured local-day window; it never posts a second movement. An overdue occurrence stays expected until the user acts; it never becomes missed automatically. Future dates remain calendar projections until due or a plausible early notification arrives.

This applies to PAC rules as well. A future, due or overdue **Expected PAC** is planned investment information in the recurring interface, not Gross Expenses, Net Expenses, Income, invested PAC or cash Net. Recording it manually creates one `.pacInvestment` transaction; linking a verified existing PAC transaction adds no second movement. Notification formats using `.pacInvestment` feed the same actual PAC total after parser and duplicate checks. A user-reported Build 9 view placed Expected PAC under Total Expenses; current main's occurrence/transaction separation and kind mapping do not reproduce that classification. Synthetic regression tests now pin the expected, missed, skipped, manual, imported-linked and notification PAC paths. No historical transaction is silently reclassified.

## Local identity and migration

SQLite schema 6 preserves each `rule UUID | scheduled local YYYY-MM-DD` occurrence ID. The 5→6 migration preserves every transaction UUID, tombstone, operation, parser event, imported source ID and original row. A schema-5 `materialized` occurrence whose transaction is active becomes `legacy_counted` with the same effective transaction. If that transaction was already soft-deleted, the occurrence becomes uncounted `expected`, retains the old UUID as provisional provenance, and displays a review reason. `skipped` remains skipped. Migration runs in `BEGIN IMMEDIATE` with foreign-key and integrity checks before commit.

`recurring_occurrences_local` can hold `expected`, `legacy_counted`, `recorded_manual`, `confirmed`, `skipped`, `missed`, or `cancelled`. Only the three counted states have an effective `transaction_id`; ledger totals still read active transactions only. A partial unique index allows a tombstoned provisional transaction to retain its occurrence reference while one active actual transaction takes the same occurrence ID. `recurring_candidates` stores pending, rejected and confirmed event/transaction pairs with reasons. `recurring_payee_aliases` stores normalized aliases approved by the user per rule. `recurring_reconciliation_audit` records state and identity changes without copying raw notification text. Each rule stores a 0–14 local-day review window, default 3.

## Matching and notifications

The parser commits the raw capture and attempt before processing. It runs its existing exact and semantic duplicate checks first, then evaluates recurring occurrences before inserting a new movement. Eligible automatic matches require the same managed account ID, compatible transaction kind, one candidate, exact EUR cents, the same scheduled **local calendar day**, an explicitly approved payee alias, and no conflicting edit or competing transaction. It never auto-matches across accounts or kinds, by amount alone, by fuzzy merchant similarity, or from an unverified legacy account label.

Within the rule's ±3-day default window, a different amount/date, unapproved payee, edited old transaction or multiple plausible occurrences creates a persistent candidate with a readable reason. Suggestions are ordered by approved payee, local-day distance, exact cents, amount difference and stable occurrence ID; multiple plausible options remain ambiguous. Variable amounts and early/late dates require user confirmation. A real parsed payment may be counted once while an uncounted expected occurrence waits for review. When an already counted legacy/manual row may be the same payment, EasyTrack holds the notification **without creating another transaction**. The source page links to recurring review; the background App Intent never opens a sheet. The review compares the captured values using the **parser-rule version stored on that attempt**. Confirming a held match attaches the event to the old UUID and, after explicit confirmation, corrects its EUR amount and date while retaining its user note/category and source history. A stale candidate, occurrence, rule or transaction revision rejects confirmation and asks for a fresh review. Rejecting or choosing Separate payment persists the decision, and a held notification can then create its own movement. Parser attempts, deduplication links, candidate state and financial edits commit together; a failed processing phase retains the raw retryable capture.

Only expense rules can settle expenses, income rules can settle income, and PAC rules can settle PAC investments. Reimbursements, advances, deposits and deposit refunds are not automatically reconciled. A link adds no financial value. Imported original currency, source values, historical rate, recoverable value and personal share are never replaced by a rule estimate. Users can record an expected payment manually, link an eligible Activity transaction, unlink a confirmed one without resurrecting an old estimate, skip an expected date, or explicitly mark an overdue expected or counted legacy/manual payment missed. A counted payment marked missed is soft-deleted only after a confirmation explaining the change to totals. Actions and source changes are audited. Future schedule edits cancel unresolved future expectations; paid history and stable IDs remain.

## Historical import and backup

A source SQLite seed is staged and validated before import. If imported movements plausibly overlap already counted legacy/manual occurrences, the preview shows **one collective conflict review**. Every pair must be marked Same payment or Separate payment; many-to-one Same choices are rejected. The preview shows account identity, both amounts/dates/descriptions, kind, reason and combined total effects. Same payment keeps the imported transaction UUID and provenance while soft-deleting the old estimate atomically. Separate payment keeps both. Expected-only dates do not block. Cancel, an incomplete decision set, changed source data or an SQL error leaves the whole ledger unchanged.

JSON backup format 7 contains all 25 schema-6 tables, including aliases, candidates and audit rows. Validation uses a disposable database and checks links, foreign keys, integrity and reopen before success. Format-5/6 backups are upgraded during validation; their preview warns that newer matching decisions absent from those files cannot be reconstructed. Replace and Merge retain the explicit policy in [backup restoration](BACKUP_RESTORE.md). CSV/XLSX export remains a read-only view of active transactions, with no extra rows for expected dates or links.

## Verification boundary

Deterministic Swift tests use fictional transactions to exercise catch-up, month-end scheduling, exact and suggested notifications, early dates, duplicate replay, multiple candidates, rejected pairs, manual actions, deleted legacy rows, 5→6 migration, collective import decisions and rollback, format-5/6 compatibility, format-7 round trip, PAC/income/personal-share totals, and CSV/XLSX regression. Focused iOS 27 simulator UI tests exercise expected and manually recorded states with relaunch, dark appearance and large text, native Files format-7 restore, a two-conflict import review with cancellation and final confirmation, source-page review followed by confirmation and unlink, manual link/skip/missed actions, and a strict exact match shown as one paid Activity row after relaunch. Real bank notification fields, locked-device Shortcuts delivery, SideStore in-place updates, iCloud Files behavior and hands-on VoiceOver remain device-only checks in [Issue #8](https://github.com/Natizh/EasyTrack/issues/8).
